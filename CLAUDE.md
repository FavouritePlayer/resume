## File structure — one master + N specialized profiles

1. **`cv_master.tex`** — verbose superset, **as complete as possible.** Named `cv_` rather than `resume_` deliberately: it isn't a resume, it's never sent, and calling it one invited confusion. Every bullet, every project, every piece of real detail that exists should live here — full technical mechanism, real numbers, full history, no trimming for space. NO page limit, and none should ever be imposed on it. **Never sent out.** This is the reservoir every specialized profile cuts from. When a role needs a bullet that was trimmed from a profile, pull it from here instead of rewriting from memory. Keep it complete and current — anything true and relevant belongs in the master even if no profile currently uses it.
2. **`resume_mle.tex`** — ONE PAGE. ML / CV emphasis. Sendable.
3. **`resume_swe.tex`** — ONE PAGE. SWE / Founder emphasis. Sendable.
4. **`resume_pm.tex`** — ONE PAGE. Product management emphasis. Sendable.
5. **`resume_research_ai.tex`** — ONE PAGE. Academic/research emphasis, targeted at AI/NLP/CV/agents research PIs. Sendable.
6. **`resume_research_robotics.tex`** — ONE PAGE. Academic/research emphasis, targeted at robotics/RL research PIs. Sendable.

These profiles (`_mle`, `_swe`, `_pm`, `_research_ai`, `_research_robotics`) are the specialized profiles that exist today, not a hard ceiling — **more specialized profiles may be added later** (e.g. a data-science-specific cut, a new-grad full-time version, a role-specific one-off). Every specialized profile, current or future, follows the same rule: it is a filtered, reordered, one-page view of the master, never an independently drafted document.

**Duplication rule:** every specialized profile shares the SAME preamble structure, fonts, and macros as the master — the same packages, the same named environments (`highlights`, `twocolentry`, etc.), the same overall visual style. Each is a *filtered, reordered view* of the master's content — not an independently styled document. If a structural/mechanism change is made (a new environment, a font change, a different bullet style), apply it consistently across master + every specialized profile.

**Exception — spacing/margin values are tuned per profile, not shared.** Page margins, `\titlespacing`, the entry-gap `\vspace`, and bullet `itemsep`/`parsep` may differ between `resume_mle.tex` and `resume_swe.tex` (and any future profile), since each has different content density. Only the underlying macros/structure stay shared; content differs per profile, and so does spacing.

**Don't chase "page fullness" as a goal — it isn't one.** Recruiters scan for content (results, keywords, structure), not for whether a page runs to the bottom margin; a resume that looks stretched to avoid whitespace reads worse, not better. Concrete rule of thumb:
- Keep margins in the normal range (~0.5–0.75in). If a profile already lands with modest trailing whitespace (roughly 10–15% of the page or less), leave it — that's normal and clean, not a defect to fix.
- Only if the empty space is conspicuously large (e.g., the bottom quarter of the page is blank) does it make sense to trim the bottom margin slightly to rebalance — and even then, not so much that the margins look noticeably tighter than a normal template.
- Never loosen line/section spacing specifically to erase whitespace once margins are already normal — that's optimizing for an appearance metric nobody is evaluating, and it risks looking padded. (Loosening spacing *for legibility* — because bullets read as cramped — is a legitimate, different reason and is fine.)
- **When a profile is built by heavily curating/cutting content (e.g. `resume_research_ai.tex` dropping most projects to stay on-theme), re-check for legitimate cut content before accepting the resulting whitespace, even if the percentage clears the 10–15% threshold.** Clearing the threshold isn't the same as being the best available page — check whether real bullets were trimmed from included projects/roles for space that could be restored now that the page has room. Real incident: `resume_research_ai.tex` (then named `resume_research.tex`) sat at ~13% trailing whitespace, technically within tolerance and reported as such at each check, but DealScout and ContextCustodian had each been cut down further than the page actually needed, dropping a real quantified metric ($\sim$4x scan-time-blowup avoided) and a real design-philosophy bullet (reversible-fix safety) that both belonged there. Restoring them dropped trailing whitespace to ~7% — matching the sibling profiles — with zero invented content. The lesson: passing the numeric threshold check is necessary but not sufficient; also ask "is there real, already-cut content I could put back."
- **Measure whitespace as "extra slack beyond the configured margin," not raw trailing-percent-of-page — the two can disagree.** `trailing = page_height − last_content_y` includes the profile's own configured bottom margin; `extra_slack = trailing − configured_margin` is the actual unused space beyond what the margin already accounts for. A file can show a moderate trailing percentage while having near-zero real slack (margin already thin, e.g. `resume_swe.tex` measured 4.1% trailing but 0.00in extra slack — fully tight), or the reverse. When extra slack is real and non-trivial (rule of thumb: $\gtrsim$0.3–0.4in), the fix is restoring genuine, already-cut content from `cv_master.tex` (per the bullet above) — never loosening line/section spacing or bumping font size to consume the space, and never shrinking margins below the 0.5in floor to chase it artificially. Real incident: `resume_mle.tex` and (pre-split) `resume_research.tex` each carried ~0.45–0.47in of real extra slack; both were fixed by restoring the `ant_sim` multi-seed-replication/regression-test bullet that was already in `cv_master.tex` but trimmed from both profiles — a real, on-theme, already-verified bullet, not padding.

## One-page policy

- **Every specialized profile is hard one page.** This applies to `_mle`, `_swe`, `_pm`, `_research_ai`, `_research_robotics`, and any specialized profile added in the future — no exceptions. For an undergrad with no PhD, a multi-page applied/SWE resume reads as not knowing the convention; recruiters skim page one anyway. The one-page constraint is what forces the weak bullets out — that's the point.
- **`cv_master.tex` is the opposite: intentionally unbounded and as verbose as possible.** It should contain everything — it's the superset, never sent, never trimmed for length. More detail in the master is always better; the page limit only applies once content is filtered into a specialized profile.
- Compile and **visually verify** each specialized profile is actually one page before declaring it done. Do not trust line counts; read the rendered PDF.

## Structural Principles (research-backed, 2026)

Rules below come from a 2025–2026 research pass on technical resume best practices for early-career/undergraduate candidates. They are permanent standards for all future edits to `cv_master.tex` and every specialized profile (`resume_mle.tex`, `resume_swe.tex`, `resume_pm.tex`, `resume_research_ai.tex`, `resume_research_robotics.tex`) — treat them as elevated/top-level even where they restate a rule already stated in more detail elsewhere in this file.

- **One page is correct and non-negotiable** for all sendable profiles (`_mle`, `_swe`, `_pm`, `_research_ai`, `_research_robotics`). This is the confirmed standard for undergraduates with under 3 years of experience — "one-page rule is dead" commentary circulating online targets experienced professionals with a decade+ of history, not this candidate. `cv_master.tex` remains the unbounded reservoir; the constraint only ever applies once content is filtered into a sendable profile. (See also "One-page policy" above.)
- **Confirmed section order per profile:**
  - `resume_swe.tex`: Education → Experience → Projects → Skills
  - `resume_mle.tex`: Education → Research → Experience → Projects → Skills — the Research section stays separate and near the top; this is standard for research-track applications, not a stylistic choice.
  - `resume_pm.tex`: Education → Experience → Projects → Skills — same skeleton as SWE; the PM differentiation is bullet framing and emphasis, not section structure.
  - `resume_research_ai.tex` and `resume_research_robotics.tex`: Education → Research → Experience → Projects → Skills — same skeleton as `resume_mle.tex`; the two research profiles differ from each other in which projects are included, not in section order.
- **Education stays first on every profile.** Do not move it below Experience — for a current undergraduate this is the correct convention, not an oversight to fix later.
- **Quantification rule (supersedes the instinct to force a number onto every bullet):** a clear, specific, true bullet with no number beats a bullet with a weak, vague, or fabricated one. Where a true metric exists, use it. Where it doesn't, quantify scope, scale, frequency, or state-change instead — "sole owner of X across Y," "shipped in 36 hours," "killed the direction after Z seeds showed no transfer" — rather than inventing a percentage or multiplier. This principle already existed narrowly (see "Known gaps" below, re: ContextCustodian, and historically DealScout before its 2026-09-05 metric update); it now applies to every bullet on every profile, not just those two.
- **PM-specific framing:** `resume_pm.tex` keeps the same underlying metrics as the technical profiles but reattaches them to decisions, not implementations. A benchmark number alone ("2.1x reward") reads as engineering; the same number attached to a judgment call ("killed an unsupported direction on evidence, shipped the validated one at 2.1x") reads as product thinking. Bullets should double as interview/case-study fodder — write each one assuming the reader may ask "tell me about a time you changed direction based on data" and the bullet should already answer it.
- **ATS formatting constraints** (verified against the current preamble — see compliance note below): single-column layout, no tables/text-boxes/graphics/headers/footers, standard section headings (no creative naming — "Experience" not "Where I've Shipped"), fonts ≥10pt, margins in the 0.5–0.75in range, PDF output. Spell out acronyms at least once on first use (e.g., "Amazon Web Services (AWS)") since keyword matching may search either the abbreviated or expanded form.
- **Never fabricate — top-level restatement.** This is already the "Traceability rule" below in full detail; restated here as a governing principle: no invented metrics, no invented tools/technologies not actually used, no embellished adjectives ("personalized," "dynamic") absent from `cv_master.tex`. Every bullet on a sendable profile must trace to the master. Flag a missing specific as a question to the user rather than inventing a plausible-sounding one.
- **Per-application keyword matching:** when tailoring toward a specific job posting, mirror 2–3 exact keywords/skills from that JD into the Skills section and relevant bullets, without keyword-stuffing. Semantic/LLM-based ATS screening increasingly penalizes stuffing in favor of natural, contextually accurate matches — a keyword that isn't true of the candidate's actual work doesn't belong regardless of what the JD wants.

**Compliance check run 2026-08-04:** the shared preamble (checked via `resume_swe.tex`) already satisfies the ATS constraints above — single column, `\pagestyle{empty}` (no header/footer), 10pt base font, `\ifPDFTeX` block with `glyphtounicode`/`pdfgentounicode` for ATS text-extraction, standard section names, margins 1.15cm top/bottom (~0.45in) × 1.6cm left/right (~0.63in) — top/bottom sits just under the 0.5in floor but within the spirit of the range; not flagged as needing a fix. The section-order discrepancy previously flagged here (`resume_swe.tex` allegedly Education → Projects → Experience → Skills) was re-checked and is resolved — the live file is Education → Experience → Projects → Skills, matching the documented order above.

This is the same failure class as the "personalized" fabrication incident below, just on the axis of *completion status* rather than *added detail* — a design-stage system described as operating is exactly as unverifiable-and-risky in an interview as an invented adjective.

## Traceability rule (hard requirement)

**Every bullet on every specialized profile must trace to real content in `cv_master.tex`.** Reframing, reordering, compressing, and merging two real bullets into one are all fine — inventing a fact, a qualifier, or a characterization that isn't in the source is not, even if it sounds plausible or is individually minor (a single invented adjective is enough to break this — see the "personalized" incident below).

- If a profile needs a rewritten framing (e.g. leading with a decision instead of a mechanism, recasting an ML metric as a product-judgment story), do the reframing — but the underlying facts, numbers, and claims must still be the ones already in the master. Don't add a new specific (a client characterization, a causal claim, a descriptive word) that isn't already stated or directly derivable from the master text.
- If a specialized profile needs content the master doesn't have, either (a) pull it from the master's fuller version of that same bullet if one exists, or (b) **ask the user rather than writing something plausible.** Do not fill a gap with an invented-but-reasonable-sounding detail.
- If a reframing gets explicitly approved for one profile (e.g. a rewritten project description), consider updating `cv_master.tex` to match, so the framing has a real source and every future profile can trace to it cleanly — don't leave the master as the only un-updated, stale version.
- **After any edit to a specialized profile that touches bullet wording, diff every changed bullet against its source in `cv_master.tex`** before considering the edit done. This isn't optional cleanup — a resume with one invented fact is a real risk (interview questions probe specifics; recruiters cross-check), not a style nitpick.
- Real incident this rule exists because of: a rewrite of `resume_pm.tex`'s IT Hired Guns bullet changed master's "dynamic updates on nearby stations, fuel prices, and offers" to "personalized offers on nearby stations and fuel prices" — "personalized" was never stated anywhere and wasn't caught until an explicit audit. Small, plausible-sounding word substitutions are exactly what this rule is meant to catch.

## Phrasing principles

- Every bullet leads with an action verb and lands a concrete result or decision. No process-description without outcome.
- Quantify where real; delete where not. A vague metric is worse than none.
- Cut adjectives that carry no information ("scalable," "production-ready," "robust") unless backed by a number.
- Recruiter-skimmable in 10 seconds. Clean, single-column, no color, ATS-readable.
- **Bold exactly one phrase per bullet, in the specialized profiles only** — the concrete result (a number, a %, a multiplier) if the bullet has one, otherwise the single decision/mechanism that makes the bullet worth reading. Never more than one bolded span per bullet: over-bolding defeats the purpose, since a skimmer's eye needs somewhere specific to land. Use `\textbf{...}` inline. `cv_master.tex` stays unbolded — it's never shown to a reviewer, so there's nothing to guide a skimmer's eye toward.

## Workflow

- Edit `.tex` directly. Compile with local MacTeX using `latexmk -pdf -aux-directory=.build -emulate-aux-dir -interaction=nonstopmode <file>.tex` (never plain `pdflatex`/`xelatex` directly — that dumps `.aux`/`.log`/etc. into the repo root instead of the gitignored `.build/` folder). Read the rendered PDF, iterate against real output until clean and (for specialized profiles) one page. See `README.md` for full setup.
- **Every `.tex` file with a pending edit gets recompiled before the turn ends — no exceptions, not just the file directly touched.** A stale `.pdf` sitting next to a newer `.tex` is a real bug: it's what actually gets sent to a recruiter or opened in a viewer, so if it doesn't match the source, the edit didn't really ship. Editing `cv_master.tex` doesn't itself require recompiling every profile (they're independent files), but any specialized profile that was touched — directly or via a cross-file fix — must have a fresh `.pdf` before considering that edit done. When several files were edited in one pass, recompile all of them in the same pass, not "whichever one I happened to check last."
- Keep the master as complete and verbose as possible; derive every specialized one-pager from it by cutting, not by drafting fresh.
- **Orphan-line check (mandatory after any edit that changes wrapping, including adding bold spans):** after compiling, render each page to an image and read every bullet's line breaks specifically — not just the page count. Look for any line where only one or two words spill onto their own line (a "widow"/orphan). Bold text is slightly wider than regular text, so adding a bold span can introduce a new orphan on a line that was previously fine — always re-run this check after bolding, not just after content edits.
  When an orphan appears, resolve it in this order, not by reflexively cutting:
  1. **Page budget first.** If the profile is already over one page, the orphan gets fixed by cutting (a word, a clause, or a whole bullet) — a page-count violation outranks everything else, no exceptions.
  2. **Otherwise, judge the word/clause causing the wrap.** Is it genuinely redundant — already established elsewhere in the same job/project's other bullets, a filler adjective, a repeated qualifier — or is it real, distinguishing information (a number, a named cause, a specific decision)? Redundant → cut it, regardless of how much space exists. Real → don't cut it by default.
  3. **If it's real information and there's trailing whitespace below the last section** (room to spare on the page), prefer restoring or adding real, already-verified detail over deleting real content — check `cv_master.tex` first, since a profile bullet is often a trimmed-down cut of a fuller master bullet. The goal is a stronger bullet, not merely a full line: never pad with vague filler just to occupy space, and never invent a metric or specific that isn't already known/verified (this is the same rule as the "Known gaps" section below — it doesn't get relaxed just because there's room on the page).
  4. **If there's no real extra detail available and no room to spare**, cutting the word is still correct even if it's not strictly redundant — recruiters skim in ~10 seconds and won't miss one word, and a clean one-pager beats a technically-more-complete one that overflows or reads padded.
- **When the same new content (a title, a bullet) is copy-pasted into multiple files in one edit pass, a bug found in one copy is a bug in all the copies — check them together, not sequentially.** Real incident: a new project title was too long for the `extendedtwocolentry` column and orphaned its last word onto its own line. The title had been pasted verbatim into `cv_master.tex`, `resume_mle.tex`, and `resume_swe.tex` in the same pass. The wrap was caught and fixed in `resume_mle.tex` first, then the edit moved on to `resume_swe.tex` and compiled it *before* checking whether the identical title — already known to be too long — had the same problem there (it did) or in `cv_master.tex` (it did). The fix isn't "check every file eventually," it's: the moment a length/wrap/content bug is found in one file, `grep` for that same string across the other files immediately and fix every hit in the same pass, before moving on to unrelated changes in the next file.
- Push after each working session.
